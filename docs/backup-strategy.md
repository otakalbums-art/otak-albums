# "Віртуальний бекап-сервер" — варіанти реалізації

З ТЗ: *"віртуальний бекап сервер на випадок лагів з інтернетом і т.п. (автоматичне
перемикання при вимкненні основного сервера)"*. Це не таблиця в БД, а
інфраструктурне рішення. Варіанти (від простого до складного):

## Варіант A — покластися на Supabase (рекомендовано для старту)
Supabase Storage й Postgres на платних планах вже мають резервування на рівні
провайдера (point-in-time recovery, реплікація диска). Для більшості весільно-
/випускних фотопроєктів цього достатньо, і "бекап-сервер" з UI в адмінці
(що показано на макеті) — це просто **індикатор стану**, не окрема
інфраструктура. Дешево, швидко, менше що може зламатися.

## Варіант B — дзеркалювання Storage у другий бакет/провайдер
- Edge Function (`supabase/functions/mirror-photo`), що тригериться на
  `storage.objects insert` і копіює файл у другий бакет (напр. Cloudflare R2
  або окремий Supabase-проєкт в іншому регіоні).
- Next.js middleware перевіряє health-check основного джерела перед видачею
  signed URL; при таймауті — віддає signed URL з дзеркала.
- Рядок "Стан серверів" в адмінці (`apps/admin/app/backup/page.tsx`) тоді
  читає реальний health-check статус, а не статичний макет.

## Варіант C — повноцінний multi-region failover
Для більшого масштабу (кілька фотографів/студій, тисячі одночасних глядачів
"посилань для мам") — окрема черга завантажень (напр. через Supabase Queues
або зовнішній worker), яка пише в обидва сховища синхронно, і DNS/CDN-рівень
перемикання (Cloudflare Load Balancer з health checks).

**Рекомендація для MVP:** почати з варіанту A, закласти в схему БД (уже
зроблено) можливість пізніше додати таблицю `storage_mirrors` для варіанту B,
якщо реальне навантаження це виправдає.
